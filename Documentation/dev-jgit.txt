:linkattrs:
= Gerrit Code Review - Developing against patched JGit

[[overview]]
== Overview

Gerrit's stable-3.13 branch consumes upstream JGit `stable-7.4` via Bazel's
`http_archive`, with a small set of build-time patches in `tools/jgit/` that
revert JGit's `jakarta.servlet` 6.1 and Jetty 12 bumps so the existing Gerrit
servlet-4 stack still compiles. For CI and most local builds this is
transparent: Bazel downloads the pinned archive, verifies the SHA256,
applies the patches, and exposes the result as `@jgit`.

The patched JGit source therefore lives only inside Bazel's
external-repository cache. Eclipse projects generated by
link:dev-eclipse.html[Eclipse setup] see it as live source, because
`tools/eclipse/project.py` points the generated `.classpath` entries
directly at Bazel's materialized copy at
`$(bazel info output_base)/external/jgit`. IntelliJ's
link:dev-intellij.html[Bazel plugin] discovers `@jgit//` directly from
Bazel's view of the repositories and so sees the same source tree without
any additional setup. No script, symlink, or `modules/jgit/` working tree
is needed.

This document covers three workflows, one per use case.

[[workflows]]
== Three workflows at a glance

[cols="1,3,2", options="header"]
|=======
| # | Use case | Setup
| 1 | Just build (CI, casual local) | _none_
| 2 | Eclipse / IntelliJ breakpoints | `tools/eclipse/project.py`
| 3 | `git bisect` JGit history | `--override_repository=jgit=<clone>`
|=======

[[story-1]]
== Story 1 — CI and casual local build (zero config)

Do nothing. Bazel reads `WORKSPACE`, downloads the JGit archive from GitHub,
verifies the SHA256, applies the patches in `tools/jgit/`, and the build
proceeds. This is the canonical path for CI, release builds, and developers
who do not need to step through JGit source in an IDE.

[[story-2]]
== Story 2 — IDE source navigation and breakpoints

Run:

----
  tools/eclipse/project.py     # Eclipse; for IntelliJ, sync via the Bazel plugin
----

The script generates `.classpath` entries that point at
`$(bazel info output_base)/external/jgit/...` — the location where Bazel
has already materialized the patched JGit source. Eclipse sees that path as
a live source root: breakpoints, type navigation, and source search all
work. Bazel and the IDE read from the same physical files, so debug-info
line numbers match exactly.

No `modules/jgit/` directory, no override flag, and no init scripts are
involved. When `WORKSPACE` bumps the JGit SHA, the next `bazelisk build`
repopulates `external/jgit` with the new content; the existing
`.classpath` entries are directory paths under that root and continue to
resolve unchanged. Re-run `project.py` only when JGit's module layout
itself changes (a new `org.eclipse.jgit.*` module appears or disappears),
which is rare.

[[story-3]]
== Story 3 — git bisect across real JGit history

When you need to bisect across actual JGit commits (for example, to find a
JGit-side regression that surfaces only in a Gerrit acceptance test), point
Bazel at an existing JGit clone:

----
  # one-time:
  git clone https://eclipse.gerrithub.io/eclipse-jgit/jgit ~/projects/jgit

  # before each Gerrit-side WORKSPACE JGit bump:
  cd ~/projects/jgit
  git checkout <SHA pinned in WORKSPACE>
  git apply /path/to/gerrit/tools/jgit/*.patch
----

Then in `~/.bazelrc` (or workspace-local `user.bazelrc`, not checked in):

----
  build --override_repository=jgit=/Users/<you>/projects/jgit
----

You now have full upstream JGit history for `git bisect`, with the same
servlet-4 reverts applied locally that CI applies, and Bazel resolving
`@jgit//...` against your clone.

[NOTE]
====
`--override_repository=jgit=...` *bypasses the entire `http_archive`
declaration*: Bazel does not download the pinned archive, verify the
SHA256, apply `strip_prefix`, or apply `tools/jgit/` patches. The override
target is consumed byte-for-byte as the contents of `@jgit`. That means
the developer is responsible for keeping the override target in sync with
what `http_archive` *would* produce — in particular, applying
`tools/jgit/*.patch` themselves after every `WORKSPACE` SHA bump.
Forgetting a patch silently produces broken JGit.
====

CI is unaffected: `~/.bazelrc` and workspace-local `user.bazelrc` are not
read by CI, so the `http_archive` declaration in `WORKSPACE` stays the
canonical source of truth.
