= Gerrit Code Review - JavaScript Plugin Change Dependencies API

`plugin.changeDependencies().register(provider)` lets a plugin contribute
relationships to threaded change lists. Gerrit owns ordering, rendering,
keyboard navigation, and bulk selection. Without a provider, Gerrit
constructs threads using native Git relationships and topics.

== Registration

Register one provider per plugin during plugin initialization. Registering a
second provider for the same plugin throws, including through a second API
instance. Multiple different plugins may contribute edges.

A minimal example, using two example change numbers:

[source,javascript]
----
Gerrit.install(plugin => {
  plugin.changeDependencies().register({
    async fetch({changes, signal}) {
      if (signal.aborted) return {edges: []};
      const ids = new Set(changes.map(change => change._number));
      return {
        edges: ids.has(123) && ids.has(122)
          ? [{from: 123, to: 122, type: 'depends-on'}]
          : [],
      };
    },
  });
});
----

== Requests and lifecycle

`fetch(request)` returns a promise of `{edges, changes?}`. A request contains:

* `context`: `change-list` for search results and dashboards, or
  `related-changes` for the relation chain on a change page.
* `changes`: a read-only array of change identities (`_number`, `project`,
  `branch`) and available revision identifiers (`current_revision`,
  `current_revision_number`). These are not full `ChangeInfo` objects.
* `signal`: an `AbortSignal`. Providers should pass it to cancellable work.

Gerrit batches all displayed dashboard sections into one request per provider
and view. Related-change requests include only entries known to represent
current patchsets; provider edges do not modify historical entries. Native
Git threading still includes historical entries.

A new source result, including a reload with unchanged revision identifiers,
triggers another request. Providers may coalesce overlapping network queries,
but must not keep dependency topology indefinitely just because revision IDs
are unchanged: reverse dependencies can change when another change is uploaded.

Requests are aborted when inputs change, the view disconnects, threading is
disabled, or thirty seconds elapse. Cancellation is cooperative; Gerrit ignores
responses to aborted requests even if a provider cannot cancel its transport.
Native threads render immediately. One slow or failed provider does not block
other providers. Rejections leave native relationships usable.

== Edges and result boundaries

Each edge contains numeric change numbers `from` and `to`, and a `type` of
`git` or `depends-on`. Direction is dependent to dependency. Gerrit retains
native Git edges, combines providers' edges, and deduplicates repeated edges.
Git ancestry takes priority when choosing one display parent. Multiple parents
and cycles are retained in graph data even though a change is rendered once.

For `change-list`, providers may also return `changes`, an array of additional
change identities in the network, including reverse dependencies. Gerrit loads
their normal list details using authenticated search requests; it does not render
plugin-supplied account or permission information. Missing, unreadable, merged,
and stale changes are omitted. Only members connected to a section's seed rows
are displayed. Added rows participate in ordinary keyboard and bulk selection.
Each provider may nominate up to 500 extra rows per request, loaded in batches
of 50. Backend network discovery limits can also bound the returned component.

Search pages apply their row limit after network expansion. This is a soft limit:
a connected network is kept whole even if it exceeds the page size. The next
page advances by the consumed prefix of original search results, not the number
of rendered rows, so unrelated results displaced by expansion remain reachable.
Added context rows may not match the original query and can reappear as context
on another page. Result counts and offsets refer to original query matches.
Dashboard sections expand independently without a page cutoff.

For `related-changes`, only edges between requested changes participate; the
provider cannot add entries to the relation chain. Providers returning edges
only remain compatible. Older frontends ignore the optional `changes` field.

== Topic grouping

The independent `group_topics` account preference groups and outlines visible
non-merged changes sharing a topic. It defaults to false. Topic-only grouping
does not request indexed dependency metadata or invoke dependency providers.
Providers remain controlled by the separate `threaded_changes` preference.
